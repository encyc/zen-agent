# Taiji P2 — Attention, Gates and Ops Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 把 P1 的自动环升级为可控的人机协作环：结构化 Attention（worker 等人是事实不是猜测）、zen 合并的规模阈值、worker 并发槽（人优先）、RPC workers op、panel 验收卡片，以及 P1 遗留技术债。

**Architecture:** Attention 通道复用 worker rpc 既有事件流（`ask_request` 即提问事实），RpcRunner 采集 → 注册表持久化 → snapshot 暴露 → panel 渲染卡片。合并阈值与并发槽是 supervisor 的确定性前置条件（延续"LLM 不在关键路径"）。Model 路由走 spawn 命令参数。

**Tech Stack:** 与 P0/P1 相同——Python 3.11+ / asyncio / subprocess git；React 18 / zustand / CSS Modules；node:test + Playwright。

**Spec:** `docs/superpowers/specs/2026-11-07-taiji-design.md`（附录 B 为 DSH 借鉴依据）。

## Global Constraints

（沿 P1 全量）：零新依赖；git subprocess 带超时；注册表原子写；import DAG 不许向上；`PROTOCOL_VERSION=2` 不变，新 op 双边同步（test_rpc_contract 钉死）；desktop 只用 token + i18n 双字典；注册表新字段向后兼容（旧 taiji.json 缺字段 → 默认值）。

## Review Focus

1. **阈值误判**：numstat 对 merge commit / 空 diff 的边界 → 阈值测试覆盖 0 行与巨型 diff。→ Task 1。
2. **槽位死锁**：spawn 排队时 kill/message 与槽释放的交错 → 测试排队中 kill。→ Task 2。
3. **Attention 陈旧**：上一轮的提问在下一轮开始后必须失效 → 测试新回合清空旧 attention。→ Task 5。
4. **旧注册表兼容**：无 attention 字段的 taiji.json 载入不炸。→ Task 5。
5. **转问循环**：Router 回答投递回 worker 后，worker 的审批 future 必须被 resolve 而不是悬空。→ Task 7。

### Descope 记录

- **Ticket/执行器状态完全分离**（附录 B 第 4 项）：P1 的 reconcile + message-resume + kill 终结性已覆盖 solo 场景的实际需求；完整分离等到"多执行器/交接"需求出现再立项。**从 P2 移除。**

### Task 1: zen 自动合并的 diff 规模阈值

**Files:**
- Modify: `zenagent/app/taiji/supervisor.py`（merge 前置条件 + `_diff_lines` 辅助）
- Test: `tests/test_taiji_supervisor.py`（追加）

**Interfaces:**
- Produces: 模块常量 `AUTO_MERGE_MAX_DIFF_LINES = 200`；`merge()` 新前置条件：`git diff --numstat <base>...<branch>` 的 (added+deleted) 总和 ≤ 阈值，超限返回 False（自动路径落验收问题，与脏主树同路径）。
- 测试：zen + 小 diff（≤200）→ 合并；zen + 大 diff（>200，StubRunner 写 300 行文件）→ 不合并 + 验收问题；0 行 diff（空提交）→ 合并。

- [ ] Step 1 失败测试 → Step 2 FAIL → Step 3 实现 → Step 4 PASS → Step 5 Commit `feat(taiji): auto-merge diff size threshold`

### Task 2: worker 并发槽 + 人优先

**Files:**
- Modify: `zenagent/app/taiji/supervisor.py`（槽信号量）、`zenagent/app/taiji/registry.py`（status 加 `queued`）
- Modify: `desktop/src/ui/rightbar/taijiGraph.ts`（STATUS_TABLE 加 queued → tone 'done'、key `panel.taiji.status.queued`）+ i18n 双字典
- Test: `tests/test_taiji_supervisor.py`、`desktop/tests/taijiGraph.test.ts`

**Interfaces:**
- Produces: `TaijiSupervisor(max_workers: int = 3)`（get_taiji 透传）；内部 `_slots = asyncio.Semaphore(max_workers)`；回合任务在跑 runner 前 acquire、finally release；`message()` 的人唤醒绕过排队（直接跑，不 acquire——人优先保留通道）。排队中 worker 的 record.status = `queued`，获得槽位后置 running。
- 测试（Python）：max_workers=1 → A 运行中 spawn B：runner 只见 A；A 完成后 B 自动开跑；排队中 kill B → B killed 且永不执行；message() 在槽满时立即唤醒。测试（TS）：statusMeta('queued') → done tone。

- [ ] 失败测试 → FAIL → 实现 → PASS → Commit `feat(taiji): worker slots with human-priority wake`

### Task 3: Attention — worker 提问的结构化采集

**Files:**
- Modify: `zenagent/app/taiji/supervisor.py`（RpcRunner 采集 ask_request 事件 → TurnResult.attention；record.attention 持久化；回合开始清旧值；里程碑注入携带提问）
- Modify: `zenagent/app/taiji/registry.py`（WorkerRecord.attention: str = ""，load 兼容缺字段）
- Modify: `zenagent/app/taiji/snapshot.py`（session 行透出 attention）
- Test: `tests/test_taiji_supervisor.py`、`tests/test_taiji_snapshot.py`

**Interfaces:**
- Produces: `TurnResult.attention: dict | None`（`{"question": str, "entries": [...]}`，来自 worker 的 ask_request 事件帧）；`WorkerRecord.attention: str`（JSON 或空）；snapshot 的 worker session 行加 `attention` 字段。
- 采集细节：RpcRunner 的 on_event 里遇 `type=="ask_request"` 记录 `{"question": event.question, "entries": event.options}`（字段名以 rpc.py 实际帧为准，实现时核对）。
- 测试：loopback worker 回合中发 ask_request 事件 → TurnResult.attention 非空、record.attention 落盘、chat 摘要含问题文本；下一回合（无提问）→ record.attention 清空；旧版 taiji.json（无 attention 键）load 不炸。

- [ ] 失败测试 → FAIL → 实现 → PASS → Commit `feat(taiji): structured attention from worker questions`

### Task 5: worker 审批上浮（转问卡片闭环）

**Files:**
- Modify: `zenagent/app/taiji/supervisor.py`（RpcRunner spawn worker 不带 `--yes`；WorkerRpcClient 增加 `answer(request_id, option)`；回合内 pending ask 未决时 turn 结束前 stop 前处理）
- Modify: `zenagent/app/taiji/worker_client.py`
- Test: `tests/test_taiji_worker_client.py`、`tests/test_taiji_supervisor.py`

**Interfaces:**
- `WorkerRpcClient.answer(request_id: str, option: str) -> dict`：发 `{"type":"ask","request_id":...,"option":...}`（载荷形状以 rpc.py `_resolve_ask` 为准）。
- 语义：worker 工具审批/提问以 ask_request 事件上浮 → Attention → Router 转问 → 人的回答经 message_worker 下一回合携带——**或**（若 client 存活且 ask future 未决）直接 answer()。P2 先实现前者（每回合短生命周期子进程的既有模型），answer() 仅为后续长连接预留。
- 测试：loopback 中 ask_request 后回合结束 → record.attention 存在、无 future 悬空告警。

- [ ] 失败测试 → FAIL → 实现 → PASS → Commit `feat(taiji): worker approval escalation via attention`
