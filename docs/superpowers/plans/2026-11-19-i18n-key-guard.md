# i18n key 一致性守卫 Implementation Plan

## 现状盘点（哪些已经有了，不重复造）

- **py 侧 zh/en 平价已有**：`tests/test_i18n.py::test_catalogs_are_key_and_
  placeholder_identical` 断言两份 catalog 键集合相等、占位符集合相等，另有
  复数对完整性测试。
- **GUI 侧 zh/en 平价已有**：`desktop/tests/locale.test.ts` 直接加载
  `messages*.ts` 钉住两 locale 平价。
- **缺失的一环：调用点校验**。`t("bad.key")` 的 fallback 是返回键名本身
  （`i18n/__init__.py::t`），GUI 侧 `useT()` 同样静默——一次重命名或手滑的
  键名不会炸任何测试，只会在某个面板上把 `tui.status.cache` 这样的原始键串
  渲染给用户。与此同时 catalog 里留下孤儿键，越积越多（三份字典 2282 行、
  每份各被改过 54 次）。

目标：**调用点字面量必须能在 catalog 里命中**，CI 级别拦住键漂移；孤儿键
只报告不强拦（存在动态键拼接）。

## 方案

### Task 1: py 调用点守卫 — `tests/test_i18n.py` 新增一个测试

用 `ast` 解析 `zenagent/**/*.py`（`__pycache__` 除外），收集所有
`Call(func=Name(id in {t, tn}))` 且第一个参数为 `ast.Constant(str)` 的字面量
键；再对 `from zenagent.i18n import …` 的实际绑定做甄别（同名遮蔽不误报：
校验该 Name 确实绑定到 `zenagent.i18n`）。断言每个字面量键 ∈ en catalog。

- 动态拼接键（`t(f"tui.{x}")` 或变量）天然不在收集范围，静默放行——守卫
  只堵"手写的字面量错键"这一类，不假装覆盖全部。
- 预跑一遍核对误报量：`grep -rE "t\('|tn\('" zenagent | wc -l` 先看基数，
  有历史漏网键就先修键再上断言。

### Task 2: GUI 调用点守卫 — `desktop/tests/i18nKeys.test.ts`

跟 `locale.test.ts` 同法：node --test 直接加载 messages 模块拿全键集合；
扫描 `desktop/src/**/*.{ts,tsx}` 中 `t('…')` / `useT()` 产物调用与
`translate(locale, '…')` 的字符串字面量第一参，断言 ∈ zh/en 键并集。
正则扫描即可（GUI 无 AST 依赖，项目此层惯例是 node --test 纯数据测试）。

### Task 3: 孤儿键报告（只报告，不 fail）

`scripts/check_i18n.py`（或并入 Task 1 的测试旁路输出）：catalog 键 − 调用点
键 = 孤儿清单，打印数量与样例。首月观察噪声水平，再决定是否收紧为 gate。
不直接进 check.sh——孤儿键很多来自"供测试使用的 test.* 键"（en.py 头部
注释已注明），需要先立排除清单。

## 明确的负范围

- **不做 ts↔py 跨栈键平价**：两套 catalog 是两个领域的文案（TUI vs GUI
  chrome），键面本来就不同源，强求并集没有意义。
- **不做代码生成/类型化 key**（`t<K extends keyof typeof en>()`）：收益是
  编译期拦截，但 ts 侧 catalog 来自运行时展开（`...panesZh`），类型化 key
  需要重排模块结构；先让守卫跑起来，若孤儿率仍高再评估。

## 验收

- `pytest tests/test_i18n.py` 新增用例全绿；故意把一个调用点键改错能红。
- `node --test desktop/tests/i18nKeys.test.ts` 全绿；同样可人为制造漂移验证。
- 三份字典的键数在报告中可见，孤儿键有基线数字。
